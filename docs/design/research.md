# Blocks — research findings → mechanisms → design decisions (rev 2)
Status: PROPOSED design research, 8 Nov 2026. Every product/capability claim cites a source opened on 8 Nov 2026 (see `sources.md`, IDs S1…S36). Lines marked **Hypothesis** are Blocks design reasoning, not sourced facts. No user testing has been done. Rev 2 updates decision cells to the lead's resolutions A1–A12; the sourced findings are unchanged.

## 1. Retrospective capture (the core mechanism)
| Finding (sourced) | Mechanism it shows | Blocks decision |
|---|---|---|
| Ableton Live "is always listening to MIDI input on armed or input-monitored tracks"; Capture MIDI retrieves what you just played without pressing Record first [S1 §19.10]. | Removes the *decide-to-record-before-you-know-it's-good* step. | Blocks listens all the time a sound is loaded; there is no arm, no record button on Play. |
| On an empty, stopped Set, Live's Capture detects and sets tempo (80–160 BPM range), sets loop boundaries, places notes on the grid, and **starts the transport playing the loop immediately** [S1 §19.10.1]. | Immediate audible confirmation of the inference; you judge by ear. | Default after Capture = loop immediately (see §6 auto-play evaluation). Inference range must be stated in UI as "count it as" alternates (×2, ½). |
| Live keeps notes played *before* the detected phrase, placed before the clip start marker, so the loop can be moved later; Crop is a separate explicit command [S1 §19.10.1]. | Non-destructive inference: the interpretation is separate from the data. | The **take** is immutable; the **grid** (tempo, beat one, loop start/length) is an editable interpretation. "Original take" is always recoverable. |
| Live recommends ending on the downbeat of the next bar to help phrase detection [S1]. Logic's stopped-mode capture discards events before a 20 s pause and hides notes before a 1.5-bar pause (still recoverable by dragging the region edge) [S7]. | Phrase segmentation uses silence/pauses; segmentation can be wrong. | Ribbon shows a dashed "likely phrase" preview **before** you press Capture; review lets you extend the loop back into earlier material. |
| When the transport is running or other clips exist, Live does **not** re-detect tempo; it uses the existing tempo and can overdub onto the playing clip [S1 §19.10.2]. | First capture defines the grid; later captures conform to it. | Grid belongs to the sketch (set by first capture). Later captures snap to the existing grid; tempo alternates are only offered on the first capture or on explicit "Re-review grid". |
| Logic Flashback Capture works playing or stopped; its button switches from dimmed to active when there is MIDI to capture [S7]; Logic for iPad has the same feature [S8]. | Capture affordance should reflect whether there is anything to capture. | Capture is never hidden; when the buffer is empty it reads "Nothing to capture yet — play something" (text, not just dimming). |
| FL Studio's Score Logger is always on, keeps the last 30 minutes per channel, offers 2/5/10/20/30-min dumps, and clears on restart [S12]. | Long rolling buffer = safety net; but a time-window dump is coarse. | Show the kept history ("1:58 kept"). **Lead decision A1:** proposed 120 s rolling history plus a hard event/byte cap. Age eviction and overload are separate states, and gaps are flagged. Recovery of uncaptured history after a restart is pending. |
| Push 3 has a dedicated Capture button; captured material goes to a new clip and plays back immediately; a track must be armed [S5]. Ableton Note (iPhone/iPad only) offers Capture MIDI that detects tempo and length and auto-loops [S6]. | A physical, single-purpose control and a phone app both converge on one-press capture + auto loop. | Capture can optionally be mapped to any spare CC/button/pad, so hands can stay on the keys. No spare pedal is required, and sustain or playing keys are never taken by default (lead decision). Note is not available on Android [S6] — a gap Blocks targets. |

## 2. Separating grid from performance (timing ambiguity)
| Finding | Mechanism | Decision |
|---|---|---|
| Live's metrical interpretation can be edited at any time with Warp Markers; tempo can change before/after recording and recordings stay in sync [S1 §19.4]. Live's quantize offers an **Amount** that moves notes by a percentage; record-quantize is a separate undo step [S1 §19.5, S2 §10.5.11]. | Three different things: interpretation (grid), playback speed (tempo), and moving notes (quantize). | Blocks has three separately named controls: **Grid** ("count it as", beat one, loop length — notes never move), **Playback tempo** ("play faster/slower" — everything moves together), **Quantise** (explicit edit with strength, undoable, original kept). |
| Live grid snapping preserves an offset relative to the note's original placement, "to preserve a groove or loose playing style" [S2 §10.2.1]. | Snap can respect feel. | Moving a captured note snaps by default with **offset preserved**; quantise default strength is 50 % for jazz-feel material, never auto-applied. **Hypothesis**: Haris will prefer feel-preserving defaults. |
| Ableton's MIDI Fact Sheet: drivers timestamp events; when monitoring, Live adds latency to the timestamp so events are recorded "at the time you hear them — not the time you play them"; Ableton prefers consistent latency over jitter [S4]. | Which instant is "the" note time is a product decision. | **Lead decision A3:** preserve input-event time. No automatic heard-time compensation without a measured delay/model. |
| Android MIDI timestamps "are based on the monotonic nanosecond system timer", consistent with audio and input timers [S27]. Web Audio `getOutputTimestamp()` relates `AudioContext` time to `performance.now()` time [S34]. | Each platform has a coherent clock bridge. | State requirement only: every buffered event carries a timestamp in one monotonic timebase per platform (native ns; web performance clock) and the UI needs `bufferStart`, `bufferEnd`, `lastEventAge`, and a mapping to audio time. Engine internals not dictated. |

## 3. Piano roll on touch
| Finding | Mechanism | Decision |
|---|---|---|
| Logic for iPad: explicit function buttons (Trim, Pencil, Brush, Velocity) "change the functionality of gestures"; Select and Copy can be **momentary** by touch-and-hold of the button [S9]. | Explicit tools plus spring-loaded quasimodes. | Three labelled tools (Edit, Draw, Range). "Add to selection" is a hold-to-use (quasimode) chip, not a sticky mode. |
| Logic for iPad: when you hold a note a second, the working area zooms horizontally for precision [S10]; VoiceOver users can move notes by drag after a hold, change length by swiping up/down, and velocity in steps of 10 [S11]. | Precision aids during drag; non-visual equivalents exist. | Loupe/magnifier during drags (no auto-zoom that moves the canvas under the finger — **Hypothesis**: less disorienting). Screen-reader custom actions mirror Logic's increments (length by grid, velocity ±10 / ±1). |
| FL Studio Mobile: tap empty grid adds a note; tap-and-hold a note to delete via pop-up; selection by tapping background, waiting for a rectangle, then dragging; time-ruler selection supports insert/delete/duplicate space [S13]. | Wait-to-select disambiguates drag intent, at a time cost. | Blocks avoids waits on the main path: in **Edit**, drag on empty = marquee immediately; navigation is always two-finger. Range tool mirrors time-ruler operations (duplicate/delete range, loop to range). |
| Ableton note editor: drag in rulers zooms/scrolls; double-click a ruler zooms to selection; velocity lane; Duplicate loop (Ctrl-D) doubles the loop and notes; deactivate notes; Split/Chop; probability [S2]. | Rulers own navigation; selection-first editing. | Rulers own 1-finger panning; double-tap ruler = zoom-to-fit; "Duplicate" acts on selection; Split/Chop/probability deferred (P2, out of scope). |
| WCAG 2.5.7: any dragging function needs a single-pointer non-drag alternative [S19]; 2.5.1: path/multipoint gestures need single-pointer alternatives [S20]. | Every drag/pinch must have a button path. | Action bar: Len −/+, Vel ±, nudge ◀▶▲▼, zoom +/−, loop steppers. |

## 4. Touch ergonomics and targets
| Finding | Decision |
|---|---|
| Android: touch targets ≥ 48×48dp (≈9 mm), separated by ≥ 8dp; recommended physical size 7–10 mm; touch area may exceed visible bounds (TouchDelegate / padding) [S15]. | All controls ≥ 48dp hit area, 8dp gaps. Small visuals (note handles) get invisible 48dp hit areas. |
| Apple HIG: default control size 44×44 pt on iOS/iPadOS, minimum 28×28 pt; spacing matters as much as size [S16]. | Web/iOS-like contexts: never below 44pt-equivalent for primary controls. |
| WCAG 2.2 SC 2.5.8 (AA): targets ≥ 24×24 CSS px or sufficiently spaced; sliders/editable areas count as one target [S17]. | Piano-roll lanes never below 24dp tall while editing is enabled; below that, taps zoom instead of edit. |
| NN/g: ≥ 1 cm × 1 cm targets; crowding causes slips; larger targets for primary actions and when users are moving [S21]. | Capture is the largest target (≥ 96dp tall). |
| Hoober (2017): people prefer to view and touch the screen centre; centre targets can be ~7 mm but corners need ~12 mm [S24]. Hoober (2013): grips change every few seconds; ~49 % one-handed, 36 % cradled, 15 % two-handed in a public-space sample; fingers obscure content [S23]. | Primary actions at bottom-centre/centre; edge/corner controls ≥ 56dp; magnifier for obscured content. **Limit**: 2013 data is older, observational, phones only, and Hoober later retracted his reach-zone drawings [S23 comments]. |

## 5. Modes, discoverability, accessibility
| Finding | Decision |
|---|---|
| NN/g: mode slips happen when the active mode is poorly signalled; use ≥ 2 redundant indicators; avoid modes where slips destroy work; spring-loaded modes prevent slips but are less discoverable [S22]. | No Erase mode (deletion is an action on a selection). Current tool shown 3 ways (pressed chip + subtitle text + grid hint). Draw-tool tap on an existing note *selects* it (never deletes). |
| WCAG 1.4.1: colour can't be the only means of conveying information [S18]. | Selection = outline weight + handles; mute = dashed + text; velocity = stem height + number; readiness = icon + text. |
| React Native exposes `accessibilityRole="adjustable"` and `accessibilityActions` incl. increment/decrement, mapped to TalkBack/VoiceOver gestures [S36]. | Steppers/sliders are adjustable; notes expose custom actions. |
| GarageBand Keyboard touch instrument: a button switches swipe behaviour between Glissando / Scroll / Pitch; four velocity-sensitivity levels; sustain can be locked [S14]. | Touch keys: explicit "Swipe: play / scroll" toggle labelled in text; sustain latch; velocity from touch position (vertical) with 3 levels. **Hypothesis**: vertical-position velocity is more reliable than pressure on Android. |

## 6. Large screens, foldables, browser constraints
| Finding | Decision |
|---|---|
| Window size classes: compact < 600dp, medium 600–840, expanded 840–1200, large 1200–1600, extra-large ≥ 1600; height compact < 480dp (99.78 % of phones in landscape); classes change at runtime (fold, rotate, multi-window) and are not device checks [S25]. | Layout keyed to width/height classes, not "isFold". Compact-height layout for phone landscape. |
| Fold-aware: `FoldingFeature` exposes state FLAT/HALF_OPENED, orientation, occlusion, isSeparating; tabletop = half-opened + horizontal hinge, content top/controls bottom; don't put controls near a separating fold [S26]. | Tabletop layout: ribbon/layers top, Capture + touch keys bottom; ±24dp hinge keep-out. |
| Chrome: an `AudioContext` created before a user gesture starts "suspended" and needs `resume()` after a gesture [S28]. `AudioContext.state` can be suspended, running, closed, or interrupted [S35]. | Web first run has a single "Start sound" tap; an "interrupted/suspended" banner with "Resume sound" at any time. |
| Chrome gates all Web MIDI behind a permission prompt (rolling out from Chrome 124); Chrome and Firefox both require permission [S29]. `requestMIDIAccess` needs a secure context and can reject with NotAllowedError/NotSupportedError [S31]. Safari (macOS, iOS) has no Web MIDI; Chrome for Android supports it; Firefox for Android does not (caniuse, 8 Nov 2026) [S30]. caniuse also lists Samsung Internet as supporting it, but we have not checked that, so Blocks does not recommend it. | Readiness states: unsupported, blocked, prompt, granted-but-no-device, connected-silent, receiving. Never show a fake "connected". |
| MIDIAccess fires `statechange` when ports are added or change state [S32]; Android MidiManager notifies device add/remove [S27]. | Disconnect/reconnect is detected live; held notes are released; buffer kept. |

## Evidence limits
- Product sources are vendor manuals/marketing; they describe capabilities, not success rates. No source quantifies how often capture inference is right.
- Hardware groovebox coverage is limited to Ableton Push 3 [S5]; Elektron/Teenage Engineering pages opened did not contain usable interaction detail and are not cited. Korg Gadget, Koala Sampler, Launchpad docs were not opened → no claims.
- Touch research is general (not musicians, not piano-roll tasks). Hoober's samples are observational and partly dated.
- Interaction-count numbers in the spec are **estimates** by walkthrough, not measurements.
